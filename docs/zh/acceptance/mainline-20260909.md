## Linux 与 Docker 真实渠道检查

操作者在新 Profile 内完成原生设备登录，并通过既有无回显 Secret 操作输入第二
测试 QQ Bot 的凭据。Mac 上原第二账号 Profile 保持停止，没有复制其认证、归档或
绑定。新账号先以拒绝策略连接：一条新私聊测试消息被归档，但未启动 Codex；随后
通过经过验证的 CLI 配置及显式 apply，只将该消息的参与者加入私聊允许名单。
群聊及其他私聊仍拒绝。

原生 Linux 完成了经过认证的 Codex Turn，原生命令审批及响应通过同一 QQ 私聊
传递。结果附件首次发送即获平台接受，并通过 QQ「另存为」下载。工作区原件、
Bridge 快照、Outbox 元数据及下载字节一致：27 字节，SHA-256 为
`7d89e074dc54482a932673a507f81591a8e7ece695d139b029eab56f4b7f6752`。
SQLite `quick_check` 通过。Linux 排空后以零退出码停止，确认没有仍使用该 Profile
Workspace 的进程后才启动 Docker。

Docker 使用 UID 1000，将同一个 Profile 挂载到相同绝对数据、Codex home 和
Workspace 路径，仅通过已支持的环境覆盖更改 Codex 可执行文件路径。容器报告
healthy，Supervisor/Profile/适配器均就绪，并恢复了同一个原生 Thread，Bridge
绑定未变。原精简镜像没有系统 CA 证书包。两个经过认证的 Turn 未推进到文件创建，
分别在 310,104 毫秒和 196,459 毫秒后显式中断；两次中断结果均到达 QQ，旧容器
随后排空并以零退出码停止。

镜像修复只将构建阶段的系统 CA 证书包复制到精简运行时，并在构建时检查它非空。
Codex 的[上游原生 TLS 实现](https://github.com/openai/codex/blob/0d46c252b3f29f10bacf0ef58a17a1aa5d17ead3/codex-rs/http-client/src/custom_ca.rs#L250)
为 WebSocket 连接器加载平台根证书。原始原生 TLS 错误文本未被保留；诊断依据是
缺失的证书包、上游代码及受控镜像对比。没有关闭 TLS 校验。

修复后镜像为
`sha256:5a23c2c3b12bba0c3b1e0863e87519afa0392b73cc835b6323276e3093729623`。
两个镜像的 Bridge 编译产物完全一致，原生 Codex 二进制 SHA-256 也相同：
`56ef98ab4032d317ab26e9b5e5a175650717351edb16ed9cde0cb6d1734d62da`。
证书包检查在原镜像失败、修复镜像通过；显式使用系统证书包的 HTTPS 探测完成
TLS 校验。该未认证探测返回的 HTTP 401 不作为模型认证证据。

修复镜像在 75,073 毫秒内完成真实认证 Turn（包括原生审批）。QQ 首次发送即接受
附件，接收端下载字节与原件、快照及 Outbox 一致：28 字节，SHA-256 为
`1c836a36fac070ec9cc5f960d4f4b8660281f3c6457042083497654a1b072ab3`。
容器重启后 Profile 和适配器重新就绪，最终以零退出码、无 OOM 停止。两个测试
容器已移除，配置、凭据、原生历史、Bridge 状态及下载文件均保留；SQLite
`quick_check` 通过。新 Linux/Docker 测试运行时目前已停止。
