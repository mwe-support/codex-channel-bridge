## 原生 Turn 期间真实断网

专用测试容器在第一个 C2C 生成帧被接受、持久前缀为 1 字符后，断开其 bridge 网络，
并在 35,739 毫秒后恢复。此操作切断了**容器全部出站网络**，包括渠道与 Codex
提供商通信，不是仅针对 QQ socket 的隔离故障。

Supervisor、worker 和原生 App Server 核心进程均保留。断网期间输入仍为 started，
答案帧处于 `sending`。恢复后，同一原生 Thread/Turn 完成，仍只有一条输入关联，
没有创建第二条输入。原生流回退到普通 Outbox；5,000、5,000、4,014 字符的三段
全部首次获平台接受并有回执。已提交正文含全部 150 个编号行及结束标记，接收客户端
可见最后一行与标记。随后新的原生请求通过恢复后的 Gateway 到达，使用所选 Luna
设置完成并交付回复。

断网期间的健康快照仍报告 `ready`。本项证明恢复及投递，不证明即时链路故障检测；
也没有判定 Gateway 使用 RESUME 还是新的 IDENTIFY，或验证 token 轮换行为。

## 生产投递路径中的响应注入

真实 C2C 探测没有产生所需拒绝条件，因此使用操作者控制的临时 Node preload，
仅在专用 Profile worker 中拦截选定测试收件人的 QQ 请求。真实 SDK HTTP 解析器
处理注入响应；其余请求仍发往真实 QQ 服务。这是**故障注入证据，不是真实平台拒绝**。
发行产物和正常启动脚本均未改变。

- **过期：**对一次流请求和一次被动终态发送注入 HTTP 400 / `304103`。生产
  适配器随后执行真实主动回退，收到 HTTP 200，最终 Outbox 首次尝试获接受；
  正确 QQ 私聊中可见准确结果。
- **限流与退避：**一次流 HTTP 429 触发完整结果回退，随后两次被动 HTTP 429
  产生持久 `retry_wait`，结果为 `deferred`。首次计划重试比观察到等待状态晚
  977 毫秒；第 3 次尝试由真实平台接受，客户端收到结果。正常停止在退出前完成了
  该投递，因此不计为待投递记录跨重启的证据。
- **待重试期间异常重启：**独立测试在第一次尝试处于 `retry_wait` 时以 SIGKILL
  终止专用容器，进程退出码 137，停止后的数据库仍保留 `retry_wait`。重启后先
  消耗一次剩余的注入 429，第 3 次尝试收到真实 HTTP 200。Outbox 记录、Logical
  Result、回复序号及正文摘要均未改变，仍只有一条输入关联，客户端收到最终结果。

较早一次原计划异常退出的测试因脚本替换未生效，实际执行了正常停止；其正常排空
及投递成功证据保留，但不计入异常重启验收。修正后的测试核对了实际 kill 命令、
137 退出码和持久待投递状态。

## 清理与结论

注入计划已禁用并移除收件人选择值。正常容器重启确认没有加载 preload，两个
适配器 ready，Luna 设置保留。核对零活动输入、零待投递 Outbox，SQLite
`quick_check` 为 `ok` 后，正常测试容器排空并零退出码停止；持久认证、配置、
历史及启动脚本保留。Mac 测试 Profile 保持 ready。

本轮覆盖的网络恢复、过期回退及限流/重启机制通过，没有在这些路径复现运行时缺陷。
**真实 C2C 过期拒绝和限流拒绝仍未观察到**，因此 FR-006 保持 `awaiting-acceptance`，
不以注入错误替代这两项平台门槛。操作者本地证据分别保存真实平台事件、注入事件、
被排除的尝试及正常启动验证。本报告不包含凭据、原始提供商身份或渠道/模型正文。
