started。随后群聊完成，接收客户端出现准确回复，两边终态投递均首次获平台接受
并有回执。

## 真实进程丢失与不确定投递

第一次 Mac App Server 崩溃暴露缺陷：恢复通知把序列化的归档去重键当成平台回复
锚点。该次被拒绝的通知保留为历史证据。
[`fc7bf4c01ea7c14fb2bf7bc0fc4564a4155f97bf`](https://github.com/mwe-support/codex-channel-bridge/commit/fc7bf4c01ea7c14fb2bf7bc0fc4564a4155f97bf)
中的共享存储修复取回 QQ/WhatsApp 原消息 ID，并保留 QQ 回复序号分配。
回归覆盖提供商/会话变体及旧式键；没有引入 schema 迁移。

修复后的 Mac 测试在一个原生帧被接受、持久前缀为 21 字符后，终止了实际 Profile
App Server。同一 Supervisor 观察到新 App Server；原输入成为 `uncertain`，原因为
`turn_result_uncertain`，没有自动重放。不确定性通知以回复序号 2 首次发送成功，
且在 QQ 可见。随后显式新请求在同一 Thread 完成并到达客户端。

原生 Linux 随后在 QQ 流状态为 `sending` 时终止实际 Profile worker；此前已有一个
被接受的帧，持久前缀为 1 字符，而客户端已经显示超出该前缀的文字。这覆盖了真实
平台已接受、确认尚未持久化的帧窗口。Supervisor 保持存活，Profile 报告
`worker_process_exit`，旧 App Server 后代全部退出。已观察自动 worker 重启，
也检查了显式 Supervisor 停止/启动。恢复协调保留一条原输入，标记
`turn_result_uncommitted`，没有重放；通知以序号 2 获接受并在 QQ 可见。
原生 Thread 模型/思考强度前后一致，显式继续请求成功。

这些测试证明不确定状态处理、通知和继续使用；不宣称恢复丢失的完整答案、崩溃流
收到 DONE 帧，或消除提供商重复窗口。

## QQ 过期与配额观测

一个真实群聊 Turn 在 369,007 毫秒后完成，但最终 Outbox 被拒绝，没有回执。
随后通过生产适配器和固定腾讯 SDK 的真实 REST 探测，在原被动回复锚点上复现
HTTP 400 / 业务码 `40034005`。适配器继而尝试主动发送，返回 HTTP 400 /
`40034105`；真实平台错误文本确认是无权限。这是已观察到的过期及回退尝试证据，
**不代表延迟结果成功送达**。Mac QQ 客户端未提供所需的机器人权限控制；仍待在
目标群开启权限后复测延迟投递。

独立私聊探测中，约 6 小时及 28 小时前的锚点仍获接受，包括开启原生流；这不能
证明无限时间窗口。有界限流探测以一秒间隔发送 21 条主动私聊消息，全部获接受，
没有观察到真实限流拒绝。上述 REST 探测使用真实生产适配器/SDK，加最小 ready
门面，没有开启第二条 Gateway 连接。确定性限流/故障契约仍作为独立证据。
